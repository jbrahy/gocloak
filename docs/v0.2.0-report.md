# goCloak v0.2.0: three fixes and a documentation pass

Branch: `v0.2.0-decouple-aws`. This is the second change on the branch; the
first was the AWS decoupling, reported separately in
[aws-decoupling-report.md](aws-decoupling-report.md) and untouched here.

Three code changes, in the order they matter.

## Fix 1: a secret leak that shipped in v0.1.0

`parseSecretRef` in `secret.go` answered a reference with no scheme by quoting
it:

```go
return "", "", fmt.Errorf("secret: reference %q has no scheme", s)
```

A caller who put a literal key where a `SecretRef` belongs therefore got the
whole key back, verbatim, inside an error that a caller logs:

```
secret: reference "jLTRL6w9l++zTSr+i3m6w61Eep/UvCa9cVtyxEKdIlg=" has no scheme
```

That violates the project's unqualified rule that secret material never
reaches a log line at any level.

The asymmetry that made it worse: `config.go`'s `validSecretRef` already
guarded the YAML path, and carries a comment explaining exactly why it must
never echo. The programmatic path had no such guard, and the programmatic path
is the one a library consumer is on. A consumer integrating goCloak by
building a `ClientConfig` in Go was on the live path.

### What changed

Every error construction in `secret.go` was reviewed, not only that line.

| Error | Before | After |
|---|---|---|
| empty reference | no echo | unchanged |
| no scheme | echoed the whole input | `noSchemeMessage`: says what shape is wanted, names `file:`, `env:` and `aws:sm:`, echoes nothing |
| malformed scheme | echoed the prefix before the first colon | `badSchemeMessage`: states the scheme charset, echoes nothing |
| empty payload | echoed the whole reference | names the scheme only |
| scheme needs a Resolver | named the scheme | unchanged, see below |
| resolver failed | names the scheme, wraps the store's error | unchanged, still scrubbed by `scrubRef` at the call sites |
| `file:` errors | name the path | unchanged, see below |
| `env:` errors | name the variable | unchanged, see below |

Two deliberate retentions, both recorded in comments in the file:

- **A scheme that has passed `validSchemeName` may be named.** It is lowercase
  and contains no colon, and neither the base64 nor the hex alphabet contains
  a colon, so a pasted key cannot reach an error through that path. Losing the
  scheme would cost the one message that tells an operator to wire up a
  `Resolver`, which is the most common real configuration mistake.
- **`file:` and `env:` errors may name their payload.** A path or a variable
  name only reaches those functions under an explicitly written `file:` or
  `env:` scheme, so it is something an operator typed, not something they
  pasted. An operator debugging a refused key needs to know which file was
  refused.

### The test, and why it can fail

`TestSecretErrorsNeverEchoTheReference` in `secret_test.go` takes six
secret-shaped inputs, including the exact value that reproduced the leak, and
asserts that no error from `parseSecretRef`, from `secretResolver.Resolve`
with and without an external resolver, from `validSecretRef`, or from
`NewClient` itself contains any 10-character window of the input. The window
rather than the whole string is what catches a partial echo, and 10 is the
smallest window that still allows the one fragment an error may legitimately
carry, a validated scheme plus its colon: the longest this project defines,
`aws:ssm:`, is eight characters.

Non-vacuity, proven by restoring the v0.1.0 line and running the test:

```
--- FAIL: TestSecretErrorsNeverEchoTheReference/jLTRL6w9l++z
    error echoes the whole reference:
      error: secret: reference "jLTRL6w9l++zTSr+i3m6w61Eep/UvCa9cVtyxEKdIlg=" has no scheme
    (two further cases fail the same way)
```

The fix was then restored and the test passes.

## Fix 2: the idle-peer log storm

`devicePeer.ipcConfig` wrote `persistent_keepalive_interval=25` for every peer
unconditionally. That is right for the client, whose one peer is the server
and whose endpoint is known when the peer is configured. It is wrong for the
server, whose peers have no endpoint until the client speaks: the timer fires,
wireguard-go has nowhere to send, and it logs at ERROR roughly every six
seconds per idle peer. A deployment with twenty occasional peers produced a
continuous stream of ERROR lines describing nothing wrong, which trains an
operator to ignore the log this project tells them to read when a handshake
fails.

The setting is now emitted only for a peer that has an endpoint.

### Spec section 8.2 is still satisfied

The keepalive is there to hold a NAT binding open and to notice a dead tunnel
quickly. Both belong to the side behind the NAT, which is the side that knows
its peer's address. The client's keepalive is what holds open the binding the
server's replies come back through; a keepalive sent from the server holds
nothing open that the client is not already holding. So this is not merely the
narrow fix, it is also the correct one: the server never needed the setting.

### Should the server apply it once it has learned an endpoint?

It would be legal. wireguard-go treats `persistent_keepalive_interval` on an
`update_only` call to an existing peer as an ordinary update: `update_only`
only prevents a missing peer from being created, and for a peer that exists
the value is applied like any other. Turning it on from zero even sets
`pkaOn`, which sends one keepalive immediately from `handlePostConfig`.

It is not done, for two reasons. The first is the paragraph above: the server
gains nothing from it. The second is cost. Nothing tells the server that an
endpoint has been learned; wireguard-go exposes no notification, so finding
out means polling `IpcGet` and parsing every peer's endpoint on a timer. That
is a new background loop, in the process that terminates hostile traffic, for
a setting with no benefit on that side. Narrow fix, deliberately.

### Tests

`TestDeviceIpcConfigKeepaliveOnlyWithAnEndpoint` asserts both halves together:
a server-side peer (no endpoint) omits the setting, on a create and on an
`update_only` reload, and a client-side peer (with an endpoint) includes it.
Both halves are needed, because deleting the setting everywhere would pass a
test that only checked the server side, and that would break spec section 8.2.

Non-vacuity: making the emission unconditional again fails the test on both
server-side assertions.

## Fix 3: a re-resolvable endpoint

`ClientConfig.Endpoint` was resolved once, in `NewClient`. A changed address
could only be recovered from by `Close` plus `NewClient`. A desktop
application sleeps, changes wifi and drops its VPN several times a day, so
that forced every integrator to write the same reconnect wrapper, and the
wrapper is hard: a `Client` is documented as safe for concurrent use and would
have to be swapped out from underneath its own concurrent users.

### The design

The suggested shape was taken, with one addition. A `Dial` that cannot bring
the tunnel up re-resolves a name endpoint and, if the address changed, moves
the device peer onto it before the remaining attempts. An IP literal skips DNS
entirely, exactly as before. A dial that succeeds does no lookup at all.

Where the shape needed filling in:

- **Once per dial, not once per retry.** The retry loop runs every 250ms and
  would otherwise hammer the resolver. The re-resolution happens after the
  first failed attempt and not again in that call.
- **Deduplicated across concurrent dials by a generation counter.** A dial
  records `clientEndpoint.generation` before its first attempt. If it then
  fails and finds the generation has advanced, another dial has already looked
  the name up and it uses that answer instead of making its own lookup.
- **Serialized by a one-slot channel rather than a mutex.** A mutex would make
  a waiting dial wait for the holder's budget, which could exceed its own. The
  channel is acquired with a `select` on the dial's budget, so a dial that
  runs out of time stops waiting and reports the handshake timeout that spec
  section 8.1 fixes.
- **Bounded.** The lookup context is derived from the dial's budget, so
  `context.WithTimeout` keeps the earlier deadline and a re-resolution cannot
  push a `Dial` past its `DialTimeout`.
- **Fail closed.** A lookup that errors, or that returns no addresses, ends
  the dial with that error. There is no fallback to the address that is
  already failing: an address the client cannot confirm is not one to keep
  using.

Recovery can take two dials rather than one, and this is documented rather
than worked around. WireGuard throttles handshake initiations to one per
`REKEY_TIMEOUT` (5s), so a dial whose budget runs out before the handshake to
the new address completes returns `ErrHandshakeTimeout` and the next one
succeeds. With the default 10s `DialTimeout` one dial is usually enough; the
test measures about 6.5s to recover inside a single `Dial`.

### New API surface: none

`clientEndpoint`, `endpointResolver`, `newClient` and
`(*tunnelDevice).SetPeerEndpoint` are all unexported, and `tunnelDevice`
itself is unexported, so `SetPeerEndpoint` is not reachable from outside the
package either. The exported surface listed in the invariants checklist is
unchanged.

`newClient(cfg, names)` exists because a test may not depend on what DNS says.
`NewClient` is `newClient(cfg, net.DefaultResolver)` and is the only caller
that supplies the real resolver.

### Tests

- `TestClientReresolvesAMovedEndpoint`: a client built against a name that
  resolves to a dead address recovers inside the one `Dial` the application
  already made, and carries bytes afterwards.
- `TestClientIPLiteralEndpointIsNeverLookedUp`: two halves, a dial that
  succeeds and a dial that fails, the second being the path that re-resolves a
  name. The resolver is one that fails the test if it is called at all.
- `TestClientEndpointReresolutionFailureFailsTheDial`: a lookup that errors
  and a lookup that returns nothing. Both end the dial quickly rather than at
  the budget, neither is reported as `ErrHandshakeTimeout`, and neither
  changes the address in force.
- `TestClientConcurrentDialsReresolveOnce`: eight concurrent dials through a
  moved endpoint all succeed, and at most one lookup is ever in flight. The
  resolver holds each lookup for 100ms so that overlap would be observable
  rather than merely possible.
- `TestClientConcurrentDialsAreSafe` was not modified and still passes.

One detail worth recording: the "dead" address in these tests is `192.0.2.1`
(TEST-NET-1), not a `127.0.0.0/8` address. The test server's UDP socket is
bound to the wildcard address, so every loopback address reaches it: a dead
endpoint on `127.0.0.2` would silently have been the live server, and the
tests would have asserted nothing.

Non-vacuity: disabling the re-resolution makes
`TestClientReresolvesAMovedEndpoint` fail at its full 25s budget with
`ErrHandshakeTimeout` naming the stale address.

## Documentation

- `CONTRIBUTING.md`: the idle-peer log storm was good first contribution 1 and
  is now fixed, so that section is deleted. It is replaced by finding M3 from
  `docs/final-review.md`, `deviceLogVerbose` having no non-test caller, written
  up with the trap that item carries: the obvious way to make an unused
  constant used is to add a configuration knob, and that is the wrong fix in a
  library whose constraint 5 is "prefer deleting code over adding a flag".
  The two parked concurrency residuals were considered and rejected as
  candidates: `docs/residuals-closed.md` closed both of them, so neither is
  open.
- `docs/integration-guide.md`: a new subsection in 5.1 on why a tunnel backend
  is an `http.RoundTripper` plus a synthetic `http://<service>` URL rather
  than a base URL, with working reverse-proxy code, which is the shape a
  desktop application in front of a WebView actually needs. A new 5.4 on the
  per-peer limits as an integration concern, found by a real integrator: raise
  the caps for HTTP workloads, set `MaxIdleConnsPerHost` so connections are
  reused rather than redialled, and treat `ErrRateLimited` as backpressure to
  back off on rather than a fatal error. A new 5.5 on an endpoint that moves.
  The stale "resolved once, at construction" line in 4.5 and the stale log
  storm note in 4.3 are gone.
- `README.md`: the quickstart no longer tells operators to expect the ERROR
  stream, and the client section documents endpoint re-resolution.
- `docs/implementation.md`: the `device.go` and `client.go` file tours, the
  client side of the connection path, the unit test list, and the "names are
  never resolved" invariant, which now states the one name that is resolved
  and why a hostile answer to it buys an attacker nothing.
- The design spec: section 5 carries an "amended in v0.2.0" note for the
  endpoint, and section 8.2's keepalive row is corrected with a new row for an
  endpoint address that changes.
